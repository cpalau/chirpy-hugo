# Internationalization Contract

i18n is a **first-class feature** in this port (decision D7). Upstream ships 33
locales; all of them are in scope from day one, and they are verified by a
dedicated gate (G7).

---

## 1. Source and target

| | Upstream | This theme |
|---|---|---|
| Location | `_data/locales/*.yml` | `i18n/*.yaml` |
| Count | 33 | 33 |
| Format | nested YAML | nested YAML (the same shape) |
| Generated | by hand | by `scripts/i18n.mjs` (normalised against `en`) |
| Editable | yes | **no** — regenerated |

Editing `i18n/*.yml` by hand is forbidden (rule R1). To change a translation,
change it upstream and re-sync (`npm run i18n`), or add an override in the
site's own `i18n/<lang>.yml`, which Hugo merges over the theme.

## 2. Locale list

33 files at v7.6.0:

`ar`, `bg-BG`, `ca-ES`, `cs-CZ`, `da-DK`, `de-DE`, `dv‑MV`, `el-GR`, `en`,
`es-ES`, `fa-IR`, `fi-FI`, `fr-FR`, `hu-HU`, `id-ID`, `it-IT`, `ja-JP`, `ko-KR`,
`ku-IQ`, `my-MM`, `nl-NL`, `ps‑AF`, `pt-BR`, `ru-RU`, `sl-SI`, `sv-SE`, `th`,
`tr-TR`, `uk-UA`, `ur-PK`, `vi-VN`, `zh-CN`, `zh-TW`.

### Filename caveat (audit finding G-25)

`dv‑MV.yml` and `ps‑AF.yml` use **U+2011 NON-BREAKING HYPHEN**, not ASCII `-`.
Any script that normalises filenames, or any store that assumes ASCII, silently
drops those two languages. `scripts/i18n.mjs` must preserve the exact filename
and emit the Hugo language key in ASCII (`dv-MV`, `ps-AF`), recording the
mapping in the generated file header.

### Missing keys in the upstream catalogue

The upstream catalogue is not uniform: several locales have no `df:` block,
some define only one of the two date formats, and others write
`categories.category_measure` as a string instead of a `{singular, plural}`
map. A dotted lookup on the string form resolves to nothing, so the theme would
render an empty unit.

The generator normalises every locale against `en.yml` (section 3), which makes
the catalogue uniform and keeps the English value as the documented fallback.
The gate compares the committed files with a fresh generation, not with the
upstream bytes, because the bytes are intentionally different.

The authoritative list is whatever exists in `_data/locales/` at the pinned tag.

## 3. Generation rules

`scripts/i18n.mjs` reads the pinned `_data/locales/*.yml` and writes `i18n/`.
It parses YAML with the `yaml` package; there is no regex parsing anywhere.

### 3.1 The nested shape is kept

Hugo reads the same nested tables as Jekyll, so a key is addressed exactly as
upstream addresses it in Liquid:

```yaml
post:
  read_time:
    prompt: read
```

```go-html-template
{{ T "post.read_time.prompt" }}
```

No flattening, no dotted keys in the file: `T` joins the path itself.

### 3.2 Every locale has the `en` key tree

Every locale is rendered with the shape of `en.yml`:

- a missing key takes the English value;
- a scalar where `en` has a map is expanded (`{singular: v, plural: v}`) when it
  is the `*_measure` shape, which is the form upstream templates read with
  `.plural | default: <string>`;
- keys that `en` does not define are dropped, because no template can reach
  them.

The result is deterministic: all 33 files have identical key trees, and a
template that reads a key can never get an empty string.

### 3.3 Folding and quoting

YAML block scalars (`>-`) are folded by the parser, exactly as Ruby folds them,
and re-emitted as quoted single-line strings. The value is unchanged; only the
representation is.

### 3.4 File names

`dv‑MV.yml` and `ps‑AF.yml` use **U+2011 NON-BREAKING HYPHEN**. Hugo rejects a
language tag that is not ASCII, so the generator renames them to `dv-MV.yml`
and `ps-AF.yml`. The language key a site declares is the ASCII form.

### 3.5 Determinism

The output is sorted by key, quoted consistently and prefixed with a generated
header. `npm run test:i18n` regenerates the catalogue in memory and fails if the
committed file differs by one byte, so the repository and the generator cannot
drift.

### 3.6 Placeholders

Placeholders stay exactly as upstream writes them (`:LICENSE_NAME`, `:THEME`).
The templates substitute them with `replace`, not with Hugo's interpolation,
because the strings are also rendered by JavaScript in some contexts.

## 5. Dates and times

Upstream stores two formats per context: a Ruby `strftime` string and a Day.js
string (`df.post.strftime`, `df.post.dayjs`).

Two rendering paths exist and **both must be preserved**:

1. **Server-side**: Liquid renders a formatted date into the HTML.
2. **Client-side**: `locale-datetime.js` reformats `<time datetime="…">`
   elements at runtime using the Day.js locale.

Because the visible result may be produced by Day.js, the format strings must
reach the browser exactly as upstream sends them. During F0 the port must
confirm **where** the Day.js format string is injected (i18n bundle or data
attribute) and preserve it byte-for-byte.

The parity gate compares the final DOM **after** JavaScript execution, so a
mismatch in these strings is caught even if the raw HTML looks right.

Fallback mapping for cases where Hugo must format server-side:

| Upstream | Hugo |
|---|---|
| `%b %e, %Y` | `:date_medium` (verify against locale) or `Jan 2, 2006` |
| `ll` (Day.js) | handled client-side; do not translate to a Go layout |

Rule: **never invent a new visible date format.** If Hugo cannot produce the
exact string, keep the upstream `datetime` attribute and let the existing
JavaScript render it.

## 6. RTL

Upstream added RTL locale files in v7.4. Hugo declares direction per language:

```toml
# config/_default/languages.toml
[languages.fa]
  languageName = "فارسی"
  languageDirection = "rtl"
```

`baseof.html` must emit `<html lang="{{ .Site.Language.Lang }}" dir="{{ or .Site.Language.LanguageDirection "ltr" }}">`.

RTL locales: `ar`, `fa-IR` (and any future additions detected by the script).

Verification: Gate G7 renders each RTL locale and asserts `dir="rtl"`, and Gate
G5 captures one RTL fixture to catch layout breakage.

## 7. Language selection in the UI

**Correction (audit finding G-06):** upstream's `language-alias.html` is **not**
about UI locales. It maps *code-language identifiers* to display names
(`py` → `Python`, `rs` → `Rust`) for the label shown on code blocks. There is
**no** locale-aliasing feature in Chirpy v7.6.0.

Consequences:

- The UI language is chosen with `site.lang` (and `page.lang` per page); there is
  no built-in language switcher in the sidebar.
- Our port therefore adds nothing beyond upstream: the `<html lang>` value comes
  from the page/site language, resolved as
  `page.lang | default: alt_lang | default: site.lang`.
- If a multilingual site wants a switcher, it is a **site-level override**, not a
  theme feature, and is out of scope for v1.0 parity.
- `language-alias.html` is ported as `_partials/code-language.html` and belongs
  to the code-block pipeline, not to i18n.

## 8. `hreflang`

For every page with translations:

```go-html-template
{{ range .AllTranslations }}
  <link rel="alternate" hreflang="{{ .Language.LanguageCode }}" href="{{ .Permalink }}">
{{ end }}
<link rel="alternate" hreflang="x-default" href="{{ (index .AllTranslations 0).Permalink }}">
```

Exact markup and ordering must match upstream's `language-alias.html` output;
the parity gate covers this on multilingual fixtures only (the 12 default
fixtures are single-language).

## 9. Content translations

| Upstream | Hugo |
|---|---|
| `_posts/<lang>/post.md` | `content/posts/<slug>/index.<lang>.md` |
| tabs per language | `content/<tab>/index.<lang>.md` |
| menus per language | `menus.<lang>` in `languages.toml` |

`defaultContentLanguageInSubdir = false` by default, matching upstream's
non-prefixed default language.

## 10. Tests (Gate G7)

```bash
node scripts/i18n.mjs --check
node tests/i18n/keys.mjs
node tests/i18n/render.mjs
```

| Assertion | Detail |
|---|---|
| File count | 33 locales, names identical to upstream |
| Key parity | every locale has exactly the `en` key set |
| No empties | no null, no `""`, no whitespace-only value |
| No placeholders | no `TODO`, `TRANSLATE`, `FIXME` |
| Interpolation | keys with placeholders are used with a dict at every call site |
| Regeneration | `i18n/` regenerates byte-identically from upstream (Gate G8) |
| Render | one page per locale builds with zero errors and zero fallback warnings |
| RTL | `dir="rtl"` on `<html>` for RTL locales |
| `hreflang` | present for every translated page |
| Unused keys | a key with no call site is reported (warning, not failure) |
| Missing keys | a call site with no key is a failure |

Fallback warnings are surfaced by setting Hugo's log level to `warn` in CI for
the i18n job.

---

## 11. Adding a locale

1. Add the file upstream (preferred) and sync, **or** add a site-level override
   in `i18n/<lang>.yaml` for a personal translation.
2. Add the language to `config/_default/languages.toml`.
3. Run `node scripts/i18n.mjs --check` and Gate G7.
4. If the locale is RTL, set `languageDirection = "rtl"`.

Never edit the generated `i18n/*.yaml` in the theme.

---

## 12. Non-goals

- Machine translation of content.
- Automatic pluralization rules beyond Hugo's built-in `one`/`other`.
- Locale-specific typography beyond what upstream CSS already provides.
