# chirpy-hugo v1.0.0

The first stable release of `chirpy-hugo`: a Hugo port of
[Chirpy](https://github.com/cotes2020/jekyll-theme-chirpy) v7.6.0 that renders
the same HTML — and therefore the same pixels — as the Jekyll original.

## 1. What is new

This is the first release, so everything below is new. The short version:

- **The template layer**, ported from the pinned Jekyll theme: the document
  shell, sidebar, topbar and footer, the home and listing pages, post and page,
  the render hooks (code blocks, images, headings), the shortcodes (prompts,
  filepaths, embeds), comments, analytics, pageviews, PWA and client-side
  search.
- **All 33 upstream locales**, normalised so every locale has the same key tree
  and a missing translation falls back to English instead of disappearing.
- **The outputs the original serves**: `/feed.xml`, `/sitemap.xml`,
  `/assets/js/data/search.json`, `/assets/js/data/swconf.js` and the PWA
  manifest.
- **An installable theme**: Hugo Module (`go.mod`), a self-contained
  `exampleSite/`, a minimal `starter/`, gallery images and GitHub Actions.
- **A verification harness** that compares against a real Jekyll build: twelve
  fixtures, DOM and pixel gates, plus build integrity, HTML validity, the DOM
  contract upstream JavaScript needs, an interaction suite, accessibility,
  i18n, upstream drift and adoption gates.

## 2. What changed

- Every parameter has a default in `config/_default/params.toml`; a site with
  an empty `params` table works.
- The theme configuration documents the settings Hugo does not merge
  (`markup`, `outputs`, `menus`, and why `enableRobotsTXT` is the site's).
- CSS is precompiled with Dart Sass and committed, because Hugo cannot inject
  `@use … with ($theme: …)` for a theme and not every build ships Dart Sass
  (D-13).
- Favicons live in `static/assets/img/favicons/`: Hugo never publishes
  `assets/`, so the icons the head links to used to be 404s.

## 3. What was fixed

These were found by the gates during the port:

- Theme defaults were nested under `params.params.*`, so no default applied.
- Client-side search fetched `/assets/js/data/search.json` while the theme
  published `/search.json`.
- The service worker imported a `swconf.js` that did not exist, and the PWA
  manifest shipped Liquid tags instead of JSON.
- A subdirectory `baseURL` lost its base path on the stylesheet, the icons and
  every taxonomy link.
- Read-time counts included the `$$` delimiters of display math; footnote ids
  did not use the author's labels; the mermaid fallback missed its trailing
  newline.
- Taxonomy index metadata and JSON-LD types now follow `page.date`, exactly as
  `jekyll-seo-tag` does.

## 4. Breaking changes

None: this is the first release. Three behaviours are worth knowing before
migrating content, and they are declared in `docs/COMPATIBILITY.md`:

- **D-01**: kramdown attribute lists do not exist in Goldmark. Prompts,
  filepaths and image classes are native shortcodes; `scripts/convert-content.mjs`
  converts existing content once, with `--dry-run` and idempotent output.
- **D-14**: pagination URLs are Hugo's `/page/2/`, not Jekyll's `/page2/`.
- **D-20 and D-21**: accessibility and mobile-performance ceilings are inherited
  from upstream. The gates compare against Jekyll and fail on regressions, not
  on inherited debt.

## 5. Upstream sync

Tracks `cotes2020/jekyll-theme-chirpy` **v7.6.0**
(`152093879e6319dac342454d8df75a3c3572315f`), gem `jekyll-theme-chirpy` 7.6.0.

SCSS, JavaScript, vendored Bootstrap and the favicon set are byte-for-byte
copies, verified by sha256 (`npm run test:upstream`). The ten build artifacts
that upstream git-ignores ship committed, copied from the published gem and
never rebuilt (D-10). `scripts/sync-upstream.mjs` reports what a new upstream
release changes: copy files, manual ports, generator-owned files and retired
includes.

Measured on 2026-10-30 against a real Jekyll build of the same content:

| Gate | Result |
|---|---|
| G4 — HTML | **47/47** pages identical after canonicalization |
| G5 — pixels | **84/84** pairs identical outside the three declared rectangles (14 pages × 3 viewports × 2 themes) |

| Build | warning-free with `--panicOnWarning`, no Liquid or front matter in published files |

| Accessibility | axe: no new serious or critical finding versus Jekyll |
| Performance | desktop 99 performance / 96 best practices / 100 SEO, 0.85 s LCP; mobile within 5 points of Jekyll |

## 7. Upgrade instructions

New site:

```bash
hugo new site my-blog && cd my-blog
hugo mod init example.com/my-blog
hugo mod get github.com/cpalau/chirpy-hugo
```

Copy the mandatory sections from `starter/hugo.toml` (`outputs`,
`outputFormats`, `mediaTypes`, `markup`, `menus`, `enableRobotsTXT`), add one
post, and run `hugo server`. Everything else has a default.

From Jekyll:

1. Copy `content/` and rename `_posts` files to Hugo's layout.
2. Run `node scripts/convert-content.mjs --dry-run content/`, review, then
   `--write`.
3. Copy `_data/{authors,contact,share,media}.yml` to `data/`.
4. Delete `_config.yml`; use `starter/hugo.toml` as the base configuration.

Requirements: Hugo **extended ≥ 0.150** (tested with 0.168). Node is only
needed to run the verification harness, not to build a site.
