# chirpy-hugo v1.1.1

Bug-fix release. Two features that only work when a site enables them were
broken, and neither was covered by the corpus, so both shipped silently:

- **`params.cdn` did nothing.** `media-url.html` read `$.Site.Params.cdn` inside
  a partial called with a `dict`; `$` is the dict there, so `$.Site` is nil and
  the CDN branch never ran. Every media URL now goes through the CDN when one is
  configured, exactly as upstream's `site.cdn` does.
- **`image:` as a string crashed the build.** Upstream accepts both
  `image: /path.png` and `image: { path, alt, lqip, no_bg }`; the port
  dereferenced `.path` unconditionally and failed with
  `can't evaluate field path in type string`. `_partials/image-data.html`
  normalises both shapes, and the JSON-LD emits a plain URL for the string form,
  which is what `jekyll-seo-tag` produces (verified against the oracle).

Also fixed: the visual matrix was occasionally producing one-off pixel diffs in
the TOC column. tocbot recomputes its offsets when the capture resizes the
viewport to the page height, so the active entry changed for a few frames. The
capture now waits until it settles; the full 84-pair matrix passed three
consecutive runs.

## Coverage

The reason both bugs shipped is structural: the corpus uses the map form of
`image` and a blank `cdn`, so neither code path ever ran. The adoption gate now
carries a `--features-only` matrix (also in PR CI) that builds:

- all six analytics providers,
- the three comment providers,
- a post with `image:` as a string and another with the map form,
- media served from a CDN, asserting the absolute prefixed URLs in `og:image`,
  `twitter:image` and JSON-LD.

## Compatibility

No configuration changes. `params.cdn` now does what the documentation always
said; a site that set it will start serving media from the CDN.
