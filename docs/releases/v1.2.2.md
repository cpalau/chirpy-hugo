# chirpy-hugo v1.2.2

One declared divergence closed, and the other three explained with evidence.

## D-24 closed: the viewport meta is now identical

The upstream value is

```html
<meta name="viewport" content="width=device-width, user-scalable=no initial-scale=1, shrink-to-fit=no, viewport-fit=cover">
```

The HTML minifier collapses whitespace inside attribute values, so the port used
to emit `user-scalable=noinitial-scale=1`: an invalid viewport where the browser
drops `initial-scale` and a phone rescales the page when the off-canvas sidebar
opens. Writing the spaces as `&#32;` survives minification and decodes back to
the upstream value in the DOM. Gate 4 compares the attribute with **no
exemption** again, and the deployment gate still rejects a merged value.

The consequence is upstream's: pinch-zoom is blocked, which is an accessibility
defect. It is part of the inherited debt in D-20, and parity wins because the
attribute is part of the document. Home a11y stays at 100 on desktop in the
current Lighthouse; the post page stays at 92, as before.

## Why the other three are not closed

**D-14 — pagination URLs.** Hugo generates `/page/2/`; Jekyll generates
`/page2/`. Since Hugo 0.128 the only knob is `[pagination] path`, and it does
not substitute a page token: `page:num`, `page:num/` and `page{num}` all produce
a literal `pagenum` directory, while `page2` produces a single literal
directory. There is no configuration that yields `/page2/`, and a post-build
rename would break `hugo server` and every consumer that builds with Hugo
directly. The URL shape is D-14 and both gates normalise it.

**D-06 — the generator meta.** `jekyll-seo-tag` emits
`<meta name="generator" content="Jekyll v4.4.1">`. Reproducing it would claim
that a Hugo site was built with Jekyll — false metadata for crawlers and for
anyone debugging the page. The port emits `Hugo <version>`, which is what the
tag is for. This is the one divergence that is deliberate rather than forced.

**D-26 — an image map without `path`.** Jekyll's post header does
`page.image.path | default: page.image` and interpolates the hash, producing

```html
<a href="/{twitter" class="img-link popup shimmer">
  <img src="/{ twitter"="loading="lazy" …>
```

The port resolves the same `facebook`/`twitter` fallback the SEO tag uses and
emits a valid image with the same Open Graph tags. Reproducing the upstream
output would mean shipping invalid HTML and a broken image on purpose.

Everything else in the SEO surface is compared field by field and matches. The
map is `docs/SEO.md`.

## SEO standards, not just parity

Gate 4b now also validates the result against the specifications, so "same as
Jekyll" is not the only claim:

- **Open Graph** (`ogp.me`): `og:title`, `og:type`, absolute `og:image` and
  `og:url`, `og:url` equal to the canonical, a valid `og:locale`; `article:*`
  dates in ISO 8601 with an offset, in order.
- **Twitter cards**: valid card type, `twitter:title`, an image for
  `summary_large_image` (in either `name` or `property`, which is how upstream
  emits the fallback), well-formed `@handle`s.
- **JSON-LD**: known `@type`, its required properties, no unknown properties,
  absolute URLs, ISO dates, a valid author object, a publisher with an absolute
  logo, `headline` within 110 characters.

It runs on the fixtures (against the oracle) and on the built demo
(`npm run test:seo:demo`, 17 pages, 0 failures) and must stay **warning-free**.
The only case that would warn is upstream's fallback: `jekyll-seo-tag` uses the
author *name* for `twitter:creator`, so a site whose fallback author has no
handle would emit an invalid one. The fixtures declare both the name and the
handle; the gate reports the misconfiguration instead of hiding it.
