## 1. What this project is

`chirpy-hugo` is a **Hugo port of the Jekyll theme
[`cotes2020/jekyll-theme-chirpy`](https://github.com/cotes2020/jekyll-theme-chirpy)**.

It is **not** a rewrite, not a redesign, and not "inspired by". It is a
**contract renderer**: the same content must produce the same HTML — and
therefore the same pixels — as the Jekyll original, while upstream CSS,
JavaScript and image assets stay byte-for-byte identical.

- Baseline upstream: **v7.6.0** (`cotes2020/jekyll-theme-chirpy`)
- License: MIT, original copyright preserved (`LICENSE`, `NOTICE.md`)
- Language of all code, comments, docs and commits: **English**
- Target runtime: **Hugo extended ≥ 0.150** (local: 0.168.0 extended)

Read before changing anything:

| Document | Contents |
|---|---|
| [`docs/AUDIT.md`](docs/AUDIT.md) | **File-by-file audit of upstream v7.6.0 — source of truth** |
| [`docs/PLAN.md`](docs/PLAN.md) | Master plan, phases F0–F9, Definition of Done |
| [`docs/FEATURES.md`](docs/FEATURES.md) | Complete upstream feature inventory and Hugo mapping |

## 2. Non-negotiable rules

These are the invariants that make the project maintainable. Breaking one of
them is a bug, even if the site "looks fine".

### R1 — Assets are read-only

The following paths are **copies of upstream** and must never be edited:

```
assets/scss/         ← _sass/
assets/js/           ← _javascript/ + dist/
data/origin/         ← _data/origin/
i18n/                ← _data/locales/   (generated by scripts/i18n.mjs)
static/assets/img/favicons/ ← assets/img/favicons/
```

Exception: ten **generated** artifacts are committed, copied verbatim from the
published gem (D-10) and never hand-edited:

```
assets/js/dist/*.min.js              9 rollup bundles
assets/scss/vendors/_bootstrap.scss  purged Bootstrap
```

Both are git-ignored upstream; a Hugo consumer cannot run npm, so we ship them,
hash-verify them against the gem and never rebuild them.

If upstream CSS or JS does not fit our HTML, **the bug is in the HTML**.

### R2 — The DOM is a public contract

Do not rename classes, ids or `data-*` attributes, and do not change element
nesting relative to Jekyll output. Upstream JavaScript depends on that
structure. `tests/contract/ports.yml` records the required selectors.

Any unavoidable deviation must be:

1. recorded in `docs/COMPATIBILITY.md` with a new `D-xx` id, and
2. covered by a test that proves the consequence is harmless.

### R3 — Parity is measured, not asserted

A template is "done" when `npm run test:parity` and `npm run test:visual`
pass against the **Jekyll build of the same content**. "It looks right in my
browser" is not evidence.

### R3b — Pixel parity is 100 %, not a budget

There is **no percentage budget**. A page is correct when **zero** pixels
differ from the Jekyll render, and a single differing pixel fails Gate G5.

The only permitted exceptions are the ones declared in
`docs/COMPATIBILITY.md`, and each one must be:

1. **impossible** to reproduce in Hugo (not "hard", not "not today"),
2. **bounded**: the harness records its exact bounding box at capture time and
   counts every pixel outside those boxes, so an exemption cannot hide a
   regression somewhere else,
3. **proved harmless** by a test, and
4. listed with its `D-xx`.

Today there are exactly three, and all of them are rectangles measured on
every run:

| D-xx | Box | Why |
|---|---|---|
| D-02 | every `td.rouge-code > pre` | Chroma's token classes are not Rouge's, and two pairs are coloured differently |
| D-09 | `footer > p:nth-of-type(2)` | the footer must credit Hugo, not claim Jekyll |
| D-18 | every `audio`, `video` | the native controls live in the UA shadow DOM and are not deterministic in headless Chromium; the element, its box and its `<source>` list are still compared |

The visual gate runs **offline** (every external request aborted), captures in
one tall viewport instead of stitching a full-page shot, and finishes the whole
fourteen-page matrix in **about one minute**. If a run takes longer, something
is hanging: `capture.mjs` has a per-page ceiling and a watchdog, and
`CAPTURE_TIMEOUT_MS` bounds the process.

Anything else — one pixel, one attribute, one text node — is a bug, not a
divergence. If a page is not at zero, `docs/POC.md` §5 tracks it with an owner;
it is never silently accepted by raising a threshold.

### R4 — Build must be warning-free

`hugo --panicOnWarning --gc --minify` must pass. No `WARN`, no `ERROR`, no
deprecated API.

### R5 — English only

Code, identifiers, comments, docs, commit messages, test names. Content
fixtures may be in any language (Spanish fixtures are required for D-04).

### R6 — No magic build steps

No pre-processing of content at build time beyond what is documented in
`docs/SHORTCODES.md`. Conversion of legacy kramdown syntax is an explicit,
idempotent, dry-runnable script (`scripts/convert-content.mjs`), never an
implicit pipeline.

### R7 — Configuration is a contract

Hugo merges theme configuration with project configuration (project wins) using
per-category merge strategies: `params` uses `deep`, while `markup`, `outputs`,
`permalinks`, `module`, `languages` and `menus` do **not** merge — the project's
section replaces the theme's entirely. (Measured: a menu shipped by the theme
disappears as soon as the site declares `[menus]`.)

Consequences for this theme:

- Every parameter the theme reads must be documented in `docs/CONFIG.md` and
  must have an in-template default, so an empty `params` table still works.
- Settings in non-merging categories that the theme **requires** (`markup`:
  `unsafe`, attribute lists; `outputs` for `search.json`, `sw.js`, `swconf.js`)
  must be documented as mandatory and verified by the adoption gate (G9).
- Undocumented parameters are invisible to users.

### R8 — Follow Hugo conventions, strictly

Every template, configuration file, asset pipeline and script must follow the
**current Hugo conventions** as documented at <https://gohugo.io/>. This is not
a style preference: it is what keeps the theme upgradable, compatible with
Hugo Modules, and understandable to anyone who knows Hugo.

When this repository and the Hugo documentation disagree, **the Hugo
documentation wins**, unless a `D-xx` entry in `docs/COMPATIBILITY.md`
explains why.

Full rule set and authoritative links: [§13](#13-hugo-conventions-strict).

> Scope note: Hugo conventions govern **how the code is written**. Byte-level
> parity governs **what the output looks like**. Both apply: idiomatic Hugo
> templates that render upstream-identical HTML.

### R9 — This is a public, reusable theme

Anyone must be able to install `chirpy-hugo` in a brand-new Hugo site, with
their own content and their own configuration, and get a working site.

Therefore:

- **No personal, site-specific or project-specific content** is allowed in this
  repository: no personal domains, no migration notes for a specific blog, no
  private project names, no analytics IDs, no API keys or tokens.
- **No hardcoded personal values.** Names, emails, social links, CDN hosts and
  avatars are parameters with safe defaults.
- **It must work with an empty `params` table.** Every option is optional.
- **It must work with any content.** No assumption about sections, taxonomies,
  slugs, languages or how many posts exist.
- **It must work with any `baseURL`**, including a subdirectory deployment.
- **It must work for both monolingual and multilingual sites.**
- Examples in docs use `example.com` and neutral fixtures.

The canonical proof is the adoption gate (G9): the theme must build
`gohugoio/HugoBasicExample` and a freshly created site with no configuration.

### R10 — Follow the official Hugo theme conventions

The repository layout, metadata and distribution must match how Hugo expects a
theme to be built and shipped. This includes `archetypes/`, `assets/`,
`content/`, `data/`, `i18n/`, `layouts/`, `static/`, `theme.toml`, `images/`
and an optional self-contained `exampleSite/`.

Details and links: [§14](#14-theme-distribution-and-reusability).

### R11 — Read the Hugo documentation while writing, not after

Every template, function, configuration key and CLI flag is checked against the
**current** official documentation *before* it is written. Hugo deprecates keys
silently: they keep building and only emit a `WARN`, so code that "works" can
already be obsolete. `--panicOnWarning` is the detector, not the excuse.

Procedure and the running list of deprecations caught this way:
[§13.11](#1311-documentation-first-workflow-mandatory).

## 5. How to port a template (the core workflow)

0. **Read `docs/AUDIT.md` first.** It records what each upstream file does and
   what the expected output is. If the audit and the code disagree, the audit is
   wrong — fix it in the same PR.
1. **Read the upstream file.** Open the Liquid source at the pinned tag
   (`tests/oracle/_theme` or the upstream repo at `v7.6.0`).
   For anything inside post content, the real spec is
   `_includes/refactor-content.html`: it post-processes rendered HTML and
   defines the final markup for tables, images, task lists, code headers and
   heading anchors.
2. **Identify every input.** Each `page.*`, `site.*`, `include.*` becomes a
   parameter or a Hugo context field. Write them down; if one is a param, it
   goes into `docs/CONFIG.md`.
3. **Map Liquid → Go templates.** Use the table below.
4. **Reproduce the output markup exactly**, including whitespace-significant
   constructs, class order and attribute order.
5. **Register the file** in `tests/contract/ports.yml` (`mode: manual`,
   source → target).
6. **Add or extend a fixture** if the file introduces behaviour not yet covered.
7. **Run the gates.** Parity and visual must pass before the commit.
8. **Record divergences** in `docs/COMPATIBILITY.md` if you could not match.

Common Liquid → Go template mappings:

| Liquid | Hugo |
|---|---|
| `{% include x.html a=b %}` | `{{ partial "x.html" (dict "a" $b) }}` |
| `{% include_cached %}` | `{{ partialCached }}` with variant args |
| `{{ site.data.locales[lang].x }}` | `{{ i18n "x" }}` |
| `{% assign %}` | `{{ $x := ... }}` |
| `where_exp` | `where` + `collections.Where` or `range` + `if` |
| `group_by` | `GroupBy` / `GroupByDate` |
| `relative_url` | `relURL` |
| `absolute_url` | `absURL` |
| `jsonify` | `jsonify` (same name, different escaping — verify) |
| `date_to_xmlschema` | `.Format "2006-01-02T15:04:05Z07:00"` |
| `strip_html` | `plainify` |
| `truncate: 200` | **not** `truncate` — replicate Jekyll semantics (D-03) |
| `default:` | `default` (note argument order differs) |
| `forloop.last` | `{{ if not (last $list) }}` / index comparison |
| `capture` | `{{ $x := ... }}` with `partial` return value |

Template conventions in this repo:

- Partial names mirror upstream file names (`post-summary.html`,
  `trending-tags.html`) so `ports.yml` stays obvious.
- Partials that only render markup **return a string**; they do not print
  side effects.
- Use `partialCached` only with explicit variant keys (`.Lang`, `.Layout`).
- Never use `.Scratch` — use `.Store` / `.Page.Store`.
- Prefer `try` over silent failure for resource lookups.
- Keep Go template logic out of `layouts/*.html`; move it into `_partials/`.

### 5.1 Markdown capability matrix (measured, Hugo 0.168)

Do not guess what Goldmark supports. These are the results that shape the whole
content layer; every one of them was measured, not assumed.

| Need | Works | Does not work |
|---|---|---|
| Code attributes (`nolineno`, `file`, `start_line`) | ` ```shell {.nolineno}` — on the **info string** | `{.nolineno}` on a line after the closing fence; per-block `start_line` is broken upstream too (G-38) |
| Prompt with Markdown inside | shortcode calling `.Inner \| .Page.RenderString (dict "display" "block")` | `{{< prompt >}}` (inner stays literal) and `{{% prompt %}}` (the HTML wrapper blocks Markdown) |
| Image classes (`left`, `right`, `light`, `dark`, `shadow`) | `{{< img >}}` shortcode | `![alt](/x.png){.left}` — the attribute is emitted as literal text |
| Image size / LQIP | `{{< img width= h= lqip= >}}` | — |
| Tables, footnotes | Goldmark extensions (default on) | — |
| Task lists | narrow `replaceRE` on `.Content` (no render hook exists) | — |
| Inline code | `replaceRE` adding `language-plaintext highlighter-rouge` | bare `<code>`: no inline-code hook, and the SCSS background keys off `code.highlighter-rouge` (G-39) |
| Word count / read time | `_partials/word-count.html` (CJK-aware) | `.WordCount` — whitespace only, diverges on every CJK case (Q1) |
| JSON output | `jsonify` + the five substitutions in `tests/qa/q2-jsonify.mjs` | raw `jsonify`: escapes `<`, `>`, `&`, U+2028/9 (Q2) |
| Post neighbours | `.PrevInSection` / `.NextInSection` | `.Prev` / `.Next`: they walk every regular page, so `about` becomes a neighbour (Q3) |
| Sorting by name | ASCII-only fold + stable insertion sort with `lt` | `sort` (Unicode collator) and `lower` (folds non-ASCII) (Q4) |
| Summary truncation | rune slice `substr 0 197` + `"..."` | built-in `truncate`: word boundary and a single `…` (D-03) |
| Code token colours | structure, gutter and header reproduced | token class names: Chroma ≠ Rouge, so some colours differ (D-02, POC §3) |
| SCSS with `$theme` | `scripts/build-css.sh` (dart-sass, committed) | `resources.FromString` + `toCSS`: no import path, and not every Hugo build ships Dart Sass (D-13) |
| Pagination URLs | Hugo's `/page/2/` | `[pagination] path` is broken in 0.168; Jekyll emits `/page2/` (D-14) |
| Taxonomy labels | `_partials/taxonomy-labels.html` | Hugo lowercases taxonomy keys; the front-matter case must be recovered |
| `lastmod` | front matter only | `enableGitInfo` turns `.Lastmod` into the commit date and leaks into SEO |
| Publishing `assets/` | `scripts/build-js.mjs` and `scripts/build-css.sh` write to `static/` | Hugo does **not** publish `assets/`; Jekyll does. Every file the browser loads must be under `static/` or reached through a Hugo Pipes resource |
| Liquid-processed assets | `scripts/build-js.mjs` renders them | `assets/js/data/mathjax.js` carries front matter and `{% comment %}` blocks: copying it raw ships broken JavaScript and MathJax silently loses its delimiters |
| Code block trailing newline | inside the last token span | after `</span>` it adds an empty line to the `<pre>` (+22 px) |

Rules derived from it:

- A shortcode that renders author Markdown **must** call `RenderString` with
  `display: block`; otherwise the paragraph wrapper disappears and G4 fails.
- Never write attributes after a block: they are silently ignored.
- If a construct has no hook, use one documented `replaceRE`, never string
  surgery spread across templates.

### 5.2 The oracle loop

The Jekyll build is the only accepted definition of "correct HTML". The loop for
any template change is:

```bash
node scripts/fetch-upstream.mjs --check   # the pin has not moved
bash tests/oracle/build.sh                # .out/oracle, JEKYLL_ENV=production
hugo --destination .out/hugo              # same fixtures, same baseURL
```

Both builds must use:

- the same `baseURL` (`http://127.0.0.1:4001/`) so absolute URLs are comparable,
- `TZ=UTC` and `timezone: UTC`,
- **no** `compress_html` and no `--minify`: D-05 is tested by G1, not by G4.

Then compare with `npm run test:parity` (G4) and `npm run test:visual` (G5).
When the two builds disagree, the Jekyll side is right by definition; fix the
Hugo side or record a `D-xx`.

Never "fix" a diff by adding CSS or by editing a copied asset (R1).

## 6. How to sync upstream

Never `git merge` upstream. Follow `docs/UPSTREAM.md`:

```bash
git remote add upstream https://github.com/cotes2020/jekyll-theme-chirpy.git  # once
git fetch upstream --tags
node scripts/sync-upstream.mjs --check        # report only
node scripts/sync-upstream.mjs --apply        # copy AUTO files, transform locales
# port MANUAL files by hand, using the generated report
npm run test:all
# bump ports.yml (tag + sha) and docs/UPSTREAM.md, then commit
```

File classification is declared in `tests/contract/ports.yml`:

- `copy` — verbatim, hash-verified.
- `transform` — generated by a script (`i18n`).
- `manual` — ported by hand; the report lists them.

A release that only touches `copy` files should take minutes.

## 7. Testing gates

| Gate | Command | Proves |
|---|---|---|
| 1 | `test:build` | Every expected URL exists; no warnings; no orphan resources |
| 2 | `test:html` | Valid HTML, unique ids, working links and anchors |
| 3 | `test:contract` | Our DOM still satisfies upstream JavaScript selectors |
| 4 | `test:parity` | Our HTML equals Jekyll's, after canonicalization |
| 5 | `test:visual` | Our pixels equal Jekyll's (Playwright + pixelmatch) |
| 6 | `test:a11y` | No serious/critical axe violations; Lighthouse budgets |
| 7 | `test:i18n` | 33 locales, identical key sets, no empty values |
| 8 | `test:upstream` | Copied assets match the pinned tag and gem (`scripts/fetch-upstream.mjs --check`); ports.yml is complete |
| 9 | `test:adoption` | The theme builds any fresh site and `HugoBasicExample` with no config |

Gate 4 and Gate 5 are the definition of "pixel perfect". They compare against
a **real Jekyll build of the same content**, not against a hand-made mock.

Visual-test determinism rules (see `docs/TESTING.md`):

- Fixed container, fixed browser build, fixed `deviceScaleFactor`.
- `page.clock.setFixedTime()`.
- `animations: "disabled"`, `caret: "hide"`.
- All third-party requests blocked and stubbed (fonts, analytics, comments).
- Dynamic regions masked (pageviews, comment widgets).
- Local fonts only.

## 8. i18n rules

Full contract in `docs/I18N.md`. Summary:

- `i18n/*.yaml` is **generated** from `_data/locales/*.yml` by
  `scripts/i18n.mjs`. Never edit generated files.
- Key names mirror upstream nesting: `layout.post`, `tabs.home`,
  `panel.toc`, `post.read_time.prompt`, `df.post.strftime`.
- All 33 upstream locales ship. `en` is the reference set.
- A locale missing a key falls back to `en`; the test gate fails if the key
  set differs at all.
- Dates: upstream defines both `strftime` (Ruby) and `dayjs` formats. Hugo
  uses `time.Format` with the locale's layout; the mapping lives in
  `docs/I18N.md` and is verified by the parity gate.
- RTL locales must set `dir` on `<html>`.
- The language selector and `hreflang` alternates mirror
  `_includes/language-alias.html`.

## 9. Commits and releases

### 9.1 Commits: English + Conventional Commits (mandatory)

Every commit message is written **in English** and follows the
[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
specification. No exceptions: no Spanish, no free-form messages, no `wip`,
no `fix stuff`.

```
<type>(<scope>): <description>

[optional body, English]

[optional footer(s)]
```

Allowed types:

| Type | Use for |
|---|---|
| `feat` | a new user-visible capability |
| `fix` | a bug fix |
| `perf` | performance improvement |
| `refactor` | internal change with no behaviour change |
| `docs` | documentation only |
| `test` | tests and fixtures |
| `build` | build pipeline, dependencies, tooling |
| `ci` | CI configuration |
| `chore` | maintenance that fits nowhere else |
| `revert` | reverting a previous commit |
| `release` | version bump, changelog promotion, release notes |

Scopes: `partials`, `layouts`, `shortcodes`, `markup`, `assets`, `config`,
`i18n`, `scripts`, `tests`, `docs`, `upstream`, `starter`, `release`.

Examples:

```
feat(partials): port sidebar with social contacts
fix(seo): match jekyll-seo-tag twitter card output
chore(upstream): sync to v7.7.0
test(visual): add dark-mode snapshots for post fixtures
docs(config): document pwa.cache.deny_paths
refactor(codeblock): extract rouge table markup helper
```

Breaking changes must be signalled twice: with `!` after the type
(`feat(config)!:`) **and** a `BREAKING CHANGE:` footer explaining what breaks
and how to migrate.

Rules:

- One logical change per commit.
- A commit that changes rendered output must update the snapshots in the same
  commit.
- Never commit `public/`, `resources/`, `.out/`, `node_modules/`.
- Enforced mechanically by `commitlint` through a `commit-msg` hook
  (`commitlint.config.js`). CI re-validates the range on every push (the
  `before..sha` range) and on every PR (the `base..head` range).

### 9.2 Releases: complete, human-readable release notes (mandatory)

The technical names for what a release must contain are **release notes** and
the project **changelog**. This project uses:

- **Semantic Versioning 2.0.0** ([semver.org](https://semver.org/)) for version
  numbers: `MAJOR.MINOR.PATCH`.
- **Keep a Changelog 1.1.0** ([keepachangelog.com](https://keepachangelog.com/))
  for the structure of `CHANGELOG.md`.
- **Release notes** in the GitHub Release, derived from the changelog but
  written for a reader who does not follow the repository.

A release is **not** just a tag. Every release must explain, in English and in
full:

1. **What is new** — every feature, with a one-line explanation and an example.
2. **What changed** — behaviour changes, including anything a user might notice
   without reading the diff.
3. **What was fixed** — each bug, with the symptom and the affected version.
4. **Breaking changes** — what stops working, why, and the exact migration step.
   For a theme this includes: removed/renamed params, changed shortcodes,
   changed template paths users may have overridden, changed CSS classes or
   DOM contracts.
5. **Upstream sync** — which Chirpy version this release tracks, what was ported,
   what remains pending, and which `D-xx` divergences changed.
6. **Parity status** — the result of Gates G4 and G5, so users know whether the
   release is verified against the Jekyll original.
7. **Upgrade instructions** — the commands to run and any manual step.
8. **Credits** — upstream contributors when the work comes from Chirpy.

Nothing may be omitted because "it is in the commits": the commit log is raw
material, the release notes are the product.

`CHANGELOG.md` follows Keep a Changelog sections, always under `## [Unreleased]`
until the release is cut:

```markdown
## [Unreleased]

### Added
### Changed
### Deprecated
### Removed
### Fixed
### Security
```

Rules:

- Every merged PR adds its entry to `[Unreleased]` **in the same PR**. A PR
  without a changelog entry is rejected unless it is `docs`/`ci`/`test` only.
- The release PR moves `[Unreleased]` to `## [x.y.z] - YYYY-MM-DD`, adds the
  comparison link, and bumps `params.theme_version` and `theme.toml`.
- The GitHub Release body is the changelog section, enriched with the upstream
  sync summary and the parity report.
- A release fails if: the changelog section is empty, the version does not match
  `theme.toml`, the upstream pin is not recorded, or Gates G4/G5 are red.

Full procedure and template: [`docs/RELEASING.md`](docs/RELEASING.md).

## 10. What never to do

1. Do not edit `assets/scss/`, `assets/js/`, `data/origin/`, `i18n/`.
2. Do not add CSS overrides to compensate for template differences.
3. Do not rename classes, ids or `data-*` used by upstream JS.
4. Do not replace upstream JS with "cleaner" code.
5. Do not emulate kramdown at build time.
6. Do not add a dependency without documenting why in the PR.
7. Do not `git merge upstream/master`.
8. Do not commit visual snapshots without reviewing the diff image.
9. Do not use `truncate` where Jekyll used `truncate:` (D-03).
10. Do not claim parity without a green Gate 4 and Gate 5.
11. Do not commit personal domains, personal projects, migration notes, analytics
    IDs, tokens or any site-specific content. This repository is public.
12. Do not assume content, params or languages that a stranger's site may not
    have. If it is not optional, it is broken.
13. Do not hardcode a theme name, author, avatar or social link in templates.
14. Do not commit in any language other than English, or without a
    Conventional Commits type and scope.
15. Do not cut a release without complete release notes covering new features,
    changes, fixes, breaking changes, upstream sync and upgrade steps.

## 13. Hugo conventions (strict)

This section is the operative detail of rule **R8**. It is enforced by review.
Where a convention conflicts with byte-parity, parity wins **for the emitted
markup only**, and the reason is recorded as a `D-xx` in
`docs/COMPATIBILITY.md`. The code itself must remain idiomatic Hugo.

### 13.1 Template layout (new template system, Hugo ≥ 0.146)

```
layouts/
├── baseof.html
├── home.html
├── page.html
├── section.html
├── taxonomy.html
├── term.html
├── 404.html
├── _partials/
├── _shortcodes/
└── _markup/
```

- Use `_partials/`, `_shortcodes/` and `_markup/` (underscore-prefixed).
  The legacy `layouts/partials/` and `layouts/shortcodes/` paths are forbidden.
- Respect the template lookup order. Do not set `layout:` in front matter
  unless the content genuinely needs a distinct template.
- Use `_views/` only for content-view partials (cards, list items).
- Reference: <https://gohugo.io/templates/types/>

### 13.2 Template authoring

- Base templates define blocks; page templates fill them:

  ```go-html-template
  {{ define "main" }} ... {{ end }}
  ```

- Control whitespace with `{{-` and `-}}`; the emitted HTML must match
  upstream exactly.
- Prefer `with`, `if`, `else with`; avoid `isset` and `index` chains.
- Partials that produce a **value** must `return` it, not print it.
- Pass context explicitly with `dict` and lowercase keys; never rely on `$`.
- **Never use `.Scratch`.** Use `.Store` (`Page.Store`, `Site.Store`).
- `partialCached` only with explicit variant arguments (`.Lang`, layout name,
  output format). A cache key that ignores a variant is a bug.
- Use `.RelPermalink`, `.Permalink`, `relURL`, `absURL` — never hand-built URLs.
- `safeHTML` / `safeHTMLAttr` only on template-authored strings, never on
  content or params.
- Error handling with `try` instead of silent nil behaviour:
  <https://gohugo.io/functions/go-template/try/>
- References:
  - <https://gohugo.io/templates/introduction/>
  - <https://gohugo.io/templates/types/>
  - <https://gohugo.io/functions/partials/>

### 13.3 Configuration

- Configuration lives in `config/_default/` split by concern:
  `hugo.toml`, `params.toml`, `markup.toml`, `menus.toml`, `module.toml`,
  `languages.toml`.
- Environment overrides go in `config/<environment>/`, never in conditionals.
- All user-facing options live under `[params]`, namespaced (`params.pwa.cache.deny_paths`).
- `cascade` replaces Jekyll's `defaults`.
- Respect Hugo's per-category merge strategy: `params` is `deep` (ship defaults),
  while `markup`, `outputs`, `permalinks`, `module` and `languages` are `none`
  (the project replaces the theme section). Required settings in those
  categories must be documented and validated, never assumed.
- `pagination.pagerSize` replaces the deprecated `paginate`.
- Declare `outputs`, `outputFormats` and `mediaTypes` explicitly; do not rely
  on implicit defaults when the output is part of the contract (`search.json`,
  `sw.js`, `swconf.js`, feed).
- `timeZone` must be set explicitly.
- `enableGitInfo` is required for last-modified dates.
- References:
  - <https://gohugo.io/configuration/all/>
  - <https://gohugo.io/getting-started/directory-structure/>
  - <https://gohugo.io/configuration/markup/>

### 13.4 Assets and Hugo Pipes

- Everything goes through Hugo Pipes: `resources.Get`, `toCSS`, `postCSS`,
  `minify`, `fingerprint`.
- `resources.PostProcess` only when there is no alternative.
- Image work uses the native pipeline (`images.Filter`, `.Resize`, `.Fit`,
  `images.Overlay`), not shelling out.
- `resources.GetRemote` only with an explicit `security.http` allowlist.
- SCSS compiles with the **extended** Hugo binary (Dart Sass).
- References:
  - <https://gohugo.io/hugo-pipes/>
  - <https://gohugo.io/hugo-pipes/postcss/>
  - <https://gohugo.io/content-management/image-processing/>
  - <https://gohugo.io/configuration/security/>

### 13.5 Content, Markdown and shortcodes

- Goldmark settings are explicit and documented in `config/_default/markup.toml`.
- Prefer **render hooks** over string replacement or post-processing.
- Author-facing syntax is expressed as **shortcodes** with named parameters:

  ```go-html-template
  {{< prompt type="tip" >}} ... {{< /prompt >}}
  ```

- Use `.Inner` and `.InnerDeindent` correctly; mark shortcodes `{{< >}}` vs
  `{{% %}}` deliberately.
- Internal links use `relref` / `ref`, never hard-coded paths.
- Page bundles own their resources; use `media_subpath` only to mirror upstream
  behaviour.
- References:
  - <https://gohugo.io/templates/shortcode/>
  - <https://gohugo.io/render-hooks/>
  - <https://gohugo.io/content-management/image-processing/>

### 13.6 Internationalization

- All UI strings come from `i18n/*.yaml` via `{{ i18n "key" }}` (or `T`).
- Never concatenate translated fragments; every user-visible string is a full
  translatable unit.
- Use `.Translations`, `.AllTranslations` and `hreflang` alternates for
  multilingual sites.
- Declare languages in `config/_default/languages.toml`; `defaultContentLanguage`
  and `defaultContentLanguageInSubdir` are explicit.
- Reference: <https://gohugo.io/content-management/multilingual/>

Full project contract: [`docs/I18N.md`](docs/I18N.md).

### 13.7 Modules and distribution

- Distributed as a **Hugo Module** with semantic version tags.
- `module.mounts` are explicit; no implicit directory magic.
- `module.hugoVersion` declares the minimum supported Hugo version.
- Consumers must be able to use `hugo mod get -u` and `hugo mod vendor`.
- References:
  - <https://gohugo.io/hugo-modules/>
  - <https://gohugo.io/hugo-modules/use-modules/>
  - <https://gohugo.io/hugo-modules/theme-components/>

### 13.8 Version support and deprecations

- Minimum Hugo version is declared in `module.hugoVersion` and in `README.md`.
- CI runs the pinned version **and** the latest release.
- `hugo --panicOnWarning --printPathWarnings --gc --minify` must pass.
- Deprecation warnings are treated as errors.
- Audit helpers: <https://gohugo.io/troubleshooting/audit/> and
  <https://gohugo.io/getting-started/usage/>

### 13.9 Naming and style

- File names: lowercase, hyphen-separated, `.html` extension
  (`post-summary.html`, `render-codeblock.html`).
- One component per partial; if it needs a paragraph of explanation, split it.
- Partials mirror upstream names so `ports.yml` stays readable.
- Two-space indentation in templates.
- No inline `<style>`; no inline `<script>` except where upstream ships it and
  parity requires it (documented per case).
- No comments that restate the code; comments explain *why*.

### 13.11 Documentation-first workflow (mandatory)

Hugo moves fast and deprecates quietly. A deprecated key keeps working and only
prints a `WARN`, so "it builds" proves nothing. The documentation is consulted
**while writing**, every time.

Before writing a template, function, configuration key or CLI flag:

1. Open the page for it in §13.10 (or the functions index) and read the current
   signature, argument order and return value.
2. Read the "Deprecated" note on that page. If a replacement is named, use the
   replacement even when the old form still builds.
3. Check that the feature exists in our minimum Hugo version
   (`module.hugoVersion`, currently 0.150) and note the "added in" version.
4. Write it idiomatically — the documented example is the shape to follow.
5. Run `hugo --panicOnWarning` and treat any deprecation warning as a bug.

Two deprecations found this way on 2026-10-29, both silent until
`--panicOnWarning` / `hugo config` were run:

| Deprecated | Use instead | Since | Seen in |
|---|---|---|---|
| `languageCode` (config) | `locale` | 0.158 | `tests/fixtures/hugo/hugo.toml` |
| `.Site.Data` | `hugo.Data` | 0.156 | Q1–Q4 harness |

Rules of thumb learned from them:

- Configuration keys are the most volatile surface. Re-read
  <https://gohugo.io/configuration/all/> at the start of every phase, not just
  when something breaks.
- Prefer the *function* form over the *method* form when the docs offer both
  (`hugo.Data` over `site.Data`, `collections.Where` over method chains),
  because that is the direction Hugo is moving.
- A deprecation is never fixed by pinning an older Hugo. It is fixed by using
  the documented replacement, and the minimum version in `module.hugoVersion`
  is raised only when the replacement is genuinely newer than the floor.

## 14. Theme distribution and reusability

This theme must work for **strangers**: someone clones it into a fresh site with
their own content and no knowledge of this repository, and it just works.

### 14.1 Canonical theme skeleton

The repository layout mirrors what `hugo new theme` generates, extended with
what this project needs:

```
chirpy-hugo/
├── archetypes/          content templates for `hugo new`
├── assets/              SCSS + JS pipeline (copy of upstream)
├── content/             empty by convention; demo lives in exampleSite/
├── data/                theme data (authors, contact, share, origin)
├── i18n/                33 locales (generated)
├── images/              screenshot.png (1500×1000), tn.png (900×600)
├── layouts/             templates, partials, shortcodes, render hooks
├── static/              files served verbatim
├── theme.toml           theme metadata
├── hugo.toml            theme defaults (merged into the user's config)
├── go.mod               Hugo Module definition
├── README.md
├── LICENSE
└── exampleSite/         self-contained demo site
```

References:

- `hugo new theme`: <https://gohugo.io/commands/hugo_new_theme/>
- Directory structure: <https://gohugo.io/getting-started/directory-structure/>
- Theme components: <https://gohugo.io/hugo-modules/theme-components/>

### 14.2 `theme.toml`

Required for the Hugo theme gallery and useful for tooling. Fields:
`name`, `license`, `licenselink`, `description`, `homepage`, `demosite`, `tags`,
`features`, `min_version`, `[author]`, and an `[original]` block for the
upstream project.

### 14.3 Demo site: `exampleSite/`

- Self-contained: `hugo server --themesDir ../.. --theme chirpy-hugo`.
- Uses only public, neutral content (`example.com`, lorem-style posts).
- Must cover every documented feature, so it doubles as documentation.
- No personal data, domains, analytics IDs or tokens.

### 14.4 Installation paths that must all work

| Method | Command |
|---|---|
| Hugo Module (recommended) | `hugo mod get github.com/cpalau/chirpy-hugo` |
| Git submodule | `git submodule add … themes/chirpy-hugo` |
| Vendored | `hugo mod vendor` |
| Local | `--themesDir` |

Gate G9 verifies the module and the local path. The theme must never require
copying files into the user's project.

### 14.5 Configuration for consumers

Because Hugo's merge strategy differs per category (§13.3), the theme:

- ships **all `params` defaults** in `config/_default/params.toml` (deep merge,
  so users override only what they need);
- documents the **mandatory** settings in non-merging categories (`markup`,
  `outputs`) and detects their absence with a build warning containing the exact
  snippet to copy;
- never requires editing theme files;
- supports overriding any template by placing a file at the same path in the
  project (standard Hugo precedence).

### 14.6 Gallery submission checklist

If the theme is submitted to <https://themes.gohugo.io>:

- [ ] Repository named `hugo-theme-<name>` (the folder name is significant to
      the theme site builder).
- [ ] `theme.toml` complete.
- [ ] `README.md` descriptive, in English, with install instructions.
- [ ] `images/screenshot.png` at 1500×1000, no browser chrome.
- [ ] `images/tn.png` at 900×600.
- [ ] Builds against <https://github.com/gohugoio/HugoBasicExample>.
- [ ] `exampleSite/` provided if the theme needs demo content.
- [ ] Open an issue in the themes repository (not a pull request).

### 14.7 Reusability rules

- Zero personal values in templates, config or example content.
- No assumption about the number of posts, sections, taxonomies or languages.
- Works with `baseURL` including a subdirectory (`https://example.com/blog/`).
- Works monolingual and multilingual, with or without translations.
- Works with an empty `content/` directory (no crash, sensible empty states).
- Every feature that can be disabled is disabled by default when it needs
  external credentials (analytics, comments, pageviews).
- Missing optional data (avatar, cover image, author entry) must degrade
  gracefully, never break the build.
